# 🏗️ 콘크리트 타설 및 양생 관리 시스템 (Concrete Pouring & Curing Log)

> **Next.js 14 (App Router)**와 **Supabase**를 기반으로 구축된 건설 현장 콘크리트 타설 위치, 온도, 기상, 레미콘사, 강도/물량 및 살수/보양 양생 통합 관리 웹 애플리케이션입니다.

---

## ✨ 핵심 기능

* 📋 **엑셀 표 서식 100% 매핑**
  * `구분`, `일자`, `타설위치(동/층/벽-슬라브)`, `최저/최고온도`, `기상`, `레미콘사`, `타설강도`, `타설물량`, `양생방법(살수/보양)` 통합 테이블
* ✏️ **엑셀형 표 직접 입력 (Inline Quick Entry & Cell Editing)**
  * 표 하단 점선 빈칸 행에 직접 입력 후 `Enter` 또는 `[추가]` 클릭 시 즉시 기록
  * 기존 기록 행의 `✏️ 수정` 클릭 시 셀 단위 직관 수정 지원
* 🏢 **현장별 멀티 관리**
  * 이미지 양식의 현장 목록 기본 제공 (`대구 범어 자이 S&D`, `평택역 센트럴시티 현대 2공구`, `용인 SK FAB 지원 부속시설` 등)
  * 신규 현장 추가/삭제 관리 모달 지원
* 🚨 **스마트 양생 조건 자동 알림**
  * **서중 콘크리트 양생**: 최고온도 30°C 이상 시 살수 피복 양생 필수 알림
  * **동절기 보양 양생**: 최저온도 4°C 이하 시 방열/가온 보양 필수 알림
* 🖨️ **공식 A4 인쇄 / PDF 결재 서식**
  * 엑셀 공식 양식(작성자/검토자/승인자 결재란 포함) 그대로 내보내기 및 `window.print()` 지원
* 📑 **CSV 내보내기**
  * 엑셀 한글 깨짐 방지(UTF-8 BOM)가 적용된 CSV 내보내기 지원
* ⚡ **Supabase 자동 감지 & 실시간 DB 연동**
  * 기본 로컬 상태 및 LocalStorage 지원 + `.env.local` 입력 시 Supabase 실시간 클라우드 DB로 자동 전환

## 🚀 로컬 실행 방법 (Getting Started)

### 1. 저장소 클론 및 패키지 설치
```bash
git clone https://github.com/YOUR_USERNAME/concrete-pouring-curing-log.git
cd concrete-pouring-curing-log
npm install
```

### 2. 개발 서버 실행
```bash
npm run dev
```
브라우저에서 `http://localhost:3000` 접속 시 즉시 확인하실 수 있습니다.

## ⚡ Supabase DB 연동 가이드

1. [Supabase](https://supabase.com) 프로젝트 생성
2. Supabase **SQL Editor**에서 [`supabase/schema.sql`](./supabase/schema.sql) 스크립트 실행 (테이블 자동 생성)
3. `.env.example` 파일을 복사하여 `.env.local` 생성 후 API 키 입력:
   ```env
   NEXT_PUBLIC_SUPABASE_URL=https://your-project-id.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key-here
   ```
4. 앱 재시작 시 상단 뱃지가 **`⚡ Supabase 연동됨`**으로 바뀌며 실시간 DB로 연결됩니다.

## 동별 타설현황

기존 일지 상단의 `타설현황` 버튼 또는 `/progress`에서 현장별 현황을 관리합니다. 현장 선택은 두 페이지에서 유지되며, 기존 타설·양생 일지와 현황표의 기록은 자동으로 서로 복사되지 않습니다.

- 표 위의 `+ 동 추가`에서 동 이름·지상층 수·지하층 수를 입력하면 버림·기초·옥상·옥탑을 포함한 열을 생성합니다. 추가 후 층수를 유지하며 다음 동 이름을 제안합니다. 동·층 이름과 단계는 `동·층 관리`에서 추가·수정·삭제합니다.
- 각 동 아래에 예정일·실시일·계획 대비 차이를 함께 표시합니다. 날짜 칸은 더블클릭 또는 Enter/F2로 수정하고 Enter/저장으로 반영, Esc/취소로 되돌립니다. `26-08-20` 또는 `260820`을 입력하며 내부 저장은 `2026-08-20`을 유지합니다. 두 자리 연도는 2000~2099년입니다.
- 기존 동별 표와 배경색을 유지합니다. 오른쪽의 중복 날짜 입력과 차이 요약은 제거했고, `선택 항목 설정`에서 색상·같은 날 구역 내역을 편집합니다. 색상과 작업일 비교 단계는 선택하면 바로 저장되며 별도의 적용 버튼이 없습니다. 작업일·비교 기준은 접힌 영역에서 확인합니다. 예정·실시 작업일은 같은 비교 단계와의 날짜 간격이며, 휴일을 포함하고 시작일은 제외합니다. 계획 대비 차이는 실시일−예정일입니다.
- 표에서 한 칸을 선택하고 `선택 항목 설정 → 같은 날 부위·구역별 내역`을 펼치면 구조부위·구역·물량·비고를 여러 건 추가·수정·삭제할 수 있습니다. 동·층마다 공통 타설일 하나를 사용하며, 다른 날짜로 내역을 추가하려면 먼저 공통 날짜 변경을 확인해야 합니다. 기존 날짜·색상만 있는 v1 기록도 그대로 읽습니다.
- 실시일이 입력된 층·단계는 자동으로 타설 완료로 집계합니다. 예정일만 있거나 색상만 지정한 칸은 완료에 포함하지 않으며, 기준일 이후의 실시일도 해당 기준일의 완료 집계에서 제외합니다.
- 같은 날의 구역 내역은 완료 해제 없이 추가·수정·삭제할 수 있습니다. 기존 날짜·색상·구역 내역과 백업 형식은 유지하며, 과거 일부 타설 기록도 실시일을 기준으로 집계합니다. 불러오기만으로 기존 저장 자료를 일괄 변경하지 않습니다.
- 한 층·단계를 여러 날에 나눠 타설했으면 실시일 칸을 선택했을 때 칸 오른쪽에 나타나는 `+`로 두 번째 날짜부터 추가하거나, 화면 위에 고정된 선택 항목의 `타설일`에서 추가·삭제합니다. 표·인쇄에는 `25.04.01, 04.03, 04.05`처럼 한 줄로 표시되고 그 동의 실시일 열이 넓어지며, 완료 판단·작업일·계획 대비 차이는 마지막 타설일을 기준으로 계산합니다. CSV에는 `타설일 목록` 열이 추가되고, 날짜가 하나인 기존 기록의 저장 형식은 바뀌지 않습니다.
- 구역 내역은 현황 전용/전체 JSON 백업, 현장 보관본, CSV에 포함됩니다. 표·CSV·인쇄는 기준일 이후의 예정일·실시일과 차이도 그대로 표시합니다. CSV는 표시할 동을 따르고, 인쇄에는 구역별 내역 표를 함께 준비합니다.
- 기준일까지 완료된 가장 높은 단계와 완료 단계 수를 표시합니다. 전체 건축 공정률을 계산하지 않습니다.
- 기본 실행에서는 현황표를 Supabase `pouring_progress`에 현장별로 저장합니다. 날짜·동·층·구역·칸 색상을 함께 보존하며, 저장 버전이 달라지면 덮어쓰기를 중지합니다. 현재 현장 JSON 백업과 CSV 내보내기는 계속 지원합니다.
- 기존 `cp_pouring_progress_v1:<현장 ID>` 자료는 해당 브라우저에서 현황을 열 때 서버로 이전하며 로컬 원문은 유지합니다. 서버와 로컬에 서로 다른 자료가 있으면 자동 덮어쓰기 대신 오류를 표시합니다. `NEXT_PUBLIC_CON1_LOCAL_ONLY=true` 또는 `NEXT_PUBLIC_CON1_QA=true`에서는 기존 로컬 저장을 사용합니다.

검증: `node scripts/test-pouring-progress.cjs` (운영 DB 및 네트워크 사용 없음), `npm run build`.
날짜·계산·기존 데이터 호환 검증: `node scripts/test-progress-schedule.cjs` (예정/실시 저장, 작업일, 두 자리 연도, 백업·CSV, 실제 DB 접속 없음).
같은 날 구역별 내역 검증: `node scripts/test-same-day-progress.cjs` (기존 기록 호환, 날짜 일치, 수정·삭제, 백업, 현장 분리, CSV, 저장 실패).

현장 관리에서는 공백 차이를 포함한 같은 이름의 신규 등록을 막습니다. 이미 존재하는 동명 현장을 합치거나 삭제하지 않으며 현장 ID로 기록을 구분합니다. 현장을 삭제할 때는 현장 정보·기존 일지·현황 저장값을 `cp_site_archive_v1:` 보관본에 먼저 저장하고 다시 읽어 검증한 뒤 활성 목록에서 제거합니다. 로컬 현장은 `현장 관리 → 보관된 현장 → 현장 복원`으로 되돌릴 수 있으며, ID나 연결 기록이 충돌하면 덮어쓰지 않습니다. 복원 후에도 보관본은 유지됩니다. 보관본 저장이 실패하면 삭제를 중지하고, 이전에 남아 있던 고아 현황 데이터는 자동으로 지우지 않습니다.

보관본 역시 해당 브라우저에 있으므로 브라우저 데이터 삭제 전에 JSON 파일을 별도 보관해주세요. `자료 백업·복원`에서 전체 현장·일지·현황·삭제 보관본을 함께 내보내거나 복원할 수 있습니다. 기존 로컬 현장 보관 파일도 가져올 수 있습니다. 파일 또는 JSON 내용을 검사하고 개수를 미리 보여준 뒤 현재 브라우저의 전체 자료를 교체하며, 교체 직전 자료는 `cp_restore_recovery_v1`에 별도로 보관합니다. 복원 전 자료가 손상된 경우에도 그 원문을 보존합니다. 손상 원본 자료 백업은 보존·수리용이며 정상 백업으로 바로 가져올 수 있는 형식은 아닙니다. 현황표 전용 JSON은 타설현황 제목 줄의 `백업 저장`·`백업 불러오기`를 사용하며, 이 두 버튼은 DB 연동 상태에서도 동작합니다. DB 연동 상태에서는 전체 백업·복원을 쓸 수 없으므로 `자료 백업·복원` 메뉴를 표시하지 않습니다.

## 일지 안정성과 조회

- 현장·일지의 초기 읽기 오류가 있으면 입력을 중지하고 원본을 덮어쓰지 않습니다. 기존 일지의 렌더링 시 자동 저장은 제거했으며, 로컬 쓰기·DB 응답이 성공한 뒤 목록을 바꿉니다. 실패하면 팝업과 직접 입력의 내용이 유지됩니다.
- 두 등록 경로는 같은 초기값·검증을 사용합니다. 온도·물량·기상·양생 실시 문구는 빈값으로 시작합니다. 최근 일지의 동·구조부위·레미콘사·강도만 새 행으로 재사용할 수 있습니다.
- 기간·동·층·부위·기상·검색어(날짜·비고 포함)를 함께 조회하며, 인쇄와 CSV는 `현재 조회 결과` 또는 `현장 전체`를 선택합니다. 인쇄에는 출력 범위와 비고가 포함됩니다.
- 요약 온도는 조회 결과 기준입니다. 입력 자료가 없으면 판단할 자료 없음으로 표시하며, 양생 적합성을 자동 판정하지 않습니다.
- 다른 탭의 현장·일지 변경을 감지하고 오래된 목록으로 쓰는 작업을 차단합니다. DB의 동시 수정 충돌과 연결 복귀 시 이관은 별도 검증 대상입니다.

추가 검증: `node scripts/test-log-upgrade.cjs` (모의 DB·메모리 저장소 사용, 실제 DB/브라우저 데이터 쓰기 없음).

## 현장별 알폼핀 체결 사진

상단의 `알폼핀 체결 사진` 버튼으로 선택한 현장의 `/photos?site=현장ID` 화면을 엽니다. 촬영일(예: `26.10.26`), 동·구역, 층을 입력하고 사진을 선택하거나 오른쪽 첨부 영역에 끌어놓으면 저장합니다. 하루 장수 제한은 없으며 JPG·PNG·WebP 한 장당 20MB까지 지원합니다.

월별·날짜별 목록에서 20장씩 더 볼 수 있습니다. 보기 창은 바깥 클릭·닫기·Esc로 닫고, 확대와 원본 다운로드를 지원합니다. 삭제한 사진은 최근 삭제 취소로 복원할 수 있습니다.

사진 첨부 전에 촬영일·동·구역·층을 입력합니다. 누락 시 경고 팝업을 표시하며 사진을 보관하거나 자동 재시도하지 않습니다. 등록된 사진의 `동·층 수정`에서 위치 정보만 변경할 수 있으며 원본·미리보기·촬영일은 유지됩니다. 숫자만 입력한 위치는 `101동 · 201층`처럼 표시합니다.

## Supabase 접속 없이 실제 앱 실행 방법

PowerShell에서 다음과 같이 실행하면 실제 소스를 로컬 저장 모드로 엽니다. 이 옵션은 시작 프로세스에만 적용하며 `.env.local`의 기존 DB 설정은 바꾸지 않습니다.

```powershell
$env:NEXT_PUBLIC_CON1_LOCAL_ONLY='true'
npm run dev -- --hostname localhost --port 3000
```

로컬 전용 실행은 연결 확인과 Supabase 네트워크 요청을 차단하고 인증 세션을 읽거나 갱신하지 않습니다. 현장·일지·현황의 기존 브라우저 저장 키를 그대로 사용합니다. 브라우저 저장 데이터는 주소별로 구분되므로 기존에 사용한 브라우저와 주소를 사용해야 합니다. DB에만 있는 자료는 이 모드에서 불러오지 않습니다.
